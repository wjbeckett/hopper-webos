# First-grade client roadmap

## Shipping bar

This client should feel like a native TV product, not a browser page packaged as an IPK.

### Implemented foundation
- TV-first top navigation
- D-pad spatial focus system
- QR/device sign-in as primary authentication
- password fallback
- multi-server registry
- profile token context preservation
- Continue Watching and content rails
- Home, For You, and library Recommended screens use a shared focused-item marquee above a fixed-height, internally scrollable row band; horizontal focus changes crossfade, vertical row changes roll in the navigation direction, and logos/artwork load over color gradients
- Home/Recommended artwork is upper-right anchored and fades into a blurred color wash; the backdrop shifts with rail scrolling and receives an Android-style sampled diagonal tint when the artwork server permits safe canvas sampling
- Movies / TV / Music / Audiobooks library surfaces
- Android TV-style Library Browse sort and facet panels, including server-backed catalog facets, audiobook/video-specific sort choices, large-facet search, clear/reset, and layered remote focus/back behavior. The title-sorted Browse view also has a collapsed-dot A–Z rail; like Android TV, choosing a letter reloads the grid with the server `name_prefix` filter (`All` clears it; applying filters resets it). Sort, filters and match mode persist per server/profile/library (and media-type scope) behind a "Preserve sort & filters" toggle in the filter panel, as on Android TV. Browse cards match Android (title plus year only, white check watched badge, no progress bar, square art for audiobooks), the empty states use Android's wording, and a failed first page shows Retry and Clear filters. Not yet matched: Android's empty-library probe, and shuffle via the server launcher (webOS picks a random loaded item). Browse is a continuous list with no load-more footer; opening a title records it, and returning restores sort/filters and re-focuses that card (loading up to four further pages to find it, otherwise focusing the first card). Authenticated runtime and physical-TV validation remain open under blockers 3 and 9.
- Calendar week and Following / Trending / All filters
- Per-library Collections tab and collection detail (library_collection/user_collection scopes, collection order sort), audiobook Authors/Series group grids with drill-in, A–Z-only grid, empty-library probe, and server-backed Shuffle (`/shuffles`) for library and collection scopes. Not yet matched: music Genres pill, post-roll next-pick shuffle UI, multi-library audiobook Authors/Series (first library only), all unverified against a live server
- Movie/audiobook detail: logo or title, rating chip/year/runtime/rating facts, genre tokens, Play/Resume with Start Over, Watchlist, a More dialog (Favorite, Watched), and a Related rail from `/recommendations/similar`. Not yet matched: cast and crew, trailers/extras, versions/audio/subtitle selectors, details facts table, series Show/season tabs and next-up Play label, episode-rail edge carousel; all unverified against a live server
- Series screen: season tabs that select on focus (no Show pill). Entering from Browse or Related opens Season 1 and Play targets its first episode; a specific episode is preselected only when opened from Continue Watching/Next Up rails. Episode rows are locked to the focused season (no wrap, no cross-season scroll; Left/Right at an edge is inert). Up from the episode row lands on the active season pill and Down from a pill opens the first episode of that season, focused cards centre in the row, the rail gets page-wide right padding so the last card is not clipped, and vertical moves between the episode/cast/trailers/related rows land on the first card of the target row. Multi-library Browse pages no longer error when the server page order disagrees with the client merge guess: the loaded prefix is kept and later pages append in library order (may show a slightly mis-ordered tail for multi-library merges), episode rail with caption, air date/runtime, watched check and progress, initial focus on the next-up episode, hero that follows the focused episode with the Android metadata row (chip, Season·Episode or TV Show+genres, air date/runtime or year/seasons, ratings), the episode name inside the 3-line synopsis slot, and a bottom-locked Starring credit, Play/Resume S:E label with Start Over, direct episode playback, Watchlist, More (Shuffle Series/Season, Favorite, Mark Series/Season Watched) and Recommended Series. Also: Left/Right at a season edge jumps to the adjacent season, Starring line, Cast & Crew, Trailers & More (local extras play; YouTube launches the LG YouTube app), Related and Details sections, and a person page with filmography (shared with movie detail). Landing focus: entering a library Browse grid (and the other browse surfaces) auto-focuses the first card once items render, retrying for up to ~2s while data loads; any user keypress or existing focus cancels the retry. Series More menu rows follow Android: Shuffle Series, Shuffle Season, Favorite, Mark Episode Watched/Unwatched, Mark Series Watched/Unwatched, Mark Season Watched/Unwatched (episode entry targets the focused or next-up episode). Grounded against the live server OpenAPI (`/api/v2/docs` → openapi.json, 730 paths) and read-only probes: watched, audio/subtitle prefs bodies (server echoes `default:false` in signatures; ours omits it, matching Android), edition fields, `last_file_id`, playback-start track indexes (audio ordinal verified: `ati=1`; subtitle `-1` = off and `0..n` = ordinal into the file track list (probe-verified: stream indexes 3/4 were ignored, ordinals 0/1 took effect; the Off path now sends -1 at start instead of a post-start replan)), person detail/filmography, similar, shuffle scope kinds. Live watch state: a pub/sub (`src/core/watchState.ts`) updates every rendered MediaCard in place when Watched/Favorite changes or when playback exits (resume position) or completes (watched), so Browse, Home rails, History and detail screens reflect the new state without refetching; series-page episode toggles update the rail in place. Home and For You also re-fetch their rails ~300ms after a watch-state change (debounced, single-flight with a queued follow-up, prior rails kept if the refresh fails), and the Library Recommended screen does the same (the earlier refresh missed it: Continue Watching lives on the library rails too, so the row stayed stale until remount), mirroring Android's HomeViewModel.setWatched, which refreshes the sections on success so the server's Continue Watching/Next Up resolution shows through (a marked-watched item drops out and the surfaced replacement appears without leaving Home); when the refresh removes the focused card, focus moves to the card now in the same slot (clamped to the rail, hero follows it immediately), falling back to the first card if the whole rail is gone, and the initial landing focus no longer re-fires on rail refreshes. Realtime parity with Android's HomeRealtimeCoordinator: the app holds a `silo.events.v2` websocket (`src/api/events.ts`; `POST /events/ws-ticket` then `GET /events/ws?channels=user_state,catalog` with the ticket as a second subprotocol), subscribes to both channels, drops foreign-profile `user_state` events, and coalesces `subscribed`/`snapshot`/`user_state.changed`/`catalog` frames into a 2s-debounced rails refetch (Home, For You and Library Recommended all listen; catalogue additions surface in Recently Added without leaving the screen); reconnect uses capped backoff (1s→30s), connections are bounded by the ticket's `max_connection_seconds`, retries wait for visibility, and a 20s visible-gated poll backs the socket up. Handshake, `subscribed`/`snapshot` frames and a live `user_state.changed` (watched toggle) were verified against the test server with a raw socket probe. The Home refresh failure was then reproduced and debugged end to end in a real browser (dev app against the live server, session injected, long-press menu driven in-page): root cause was `mountedRef` in HomeScreen — `React.StrictMode` double-mounts in dev, the between-mounts cleanup set the ref false and the second mount never reset it (`useRef(true)` does not re-run), so `if (mountedRef.current) setRails(next)` skipped every refresh while the requests kept firing; the guard is gone (React drops post-unmount updates anyway). Rail rows also apply the watched change locally now (Android LocalUserStateOverlay parity): items whose `UserData.Played` is true are filtered out of Continue Watching rows on render via a bus-driven version counter, so the row updates the moment the write succeeds even if the section refetch races the server's row recompute; refetches (bus 300ms, socket signals 2s, poll 20s) reconcile. Verified in-browser after the fix: marking watched removes the entry from the row in place within ~1.5s, items added by an unwatch appear in place through the refetch clusters, and the app's events socket delivers `hello`/`subscribed` through the dev proxy. Dev proxy (`vite.config.ts`) now carries websockets (`ws: true`) and rewrites the ws handshake `Origin` to `SILO_DEV_SERVER` (the server resets proxied sockets whose Origin is not the configured origin); `eventsSocketUrl` resolves relative server URLs against `location.href` and socket construction is inside the retry path. Card long-press menus now render through a portal to `document.body`: `.home-rails` is an isolated stacking context, and the fixed scrim was trapped at the rails' z-index so the hero copy painted over the menu's top; the portal lifts the scrim into the root context above the hero and top nav. (hold OK 500ms; press releases to the card action): episode cards get Play / Mark Watched-Unwatched / Add to Favorites; MediaCard everywhere (Library Browse, Home rails, Collections, History, Calendar, Search, Person) gets Play / Mark Watched-Unwatched (except Series and Audiobook cards) / Add to Favorites, each with modal focus lock and focus return to the card; rail Up from Cast/Trailers/Related on a series page returns to the remembered episode card and Down from below the hero returns to the season pills (no row skipping). The wrapper divs that menu introduced initially stripped the episode tiles' flex sizing (each wrap became an unsized flex item with `min-width: 0`, so the tiles shrank into one another); sizing now lives on the wrapper (`flex: 0 0 clamp(220px, 18vw, 330px)`, tile `width: 100%` inside), re-verified with a rendered layout check (uniform tile widths, zero overlap, rail scrolls). Focus indication follows the Android TV grammar (`FocusModifier.kt`): scale + soft white glow, no ring — media/collection/request cards scale 1.10, focused episode tiles 1.04, non-card controls 1.06, each with a `0 0 24px rgba(255,255,255,.28)` glow over the existing shadow lift; the 2dp white focus border Android also draws is deliberately omitted on web (user preference). Focused episode tiles carry a slightly stronger glow than the card grammar (16:9 art reads dimmer at 10 ft): `0 0 26px rgba(255,255,255,.38)`. Rail tracks give the focused enlargement + glow room instead of clipping it at the scroll edge: vertical padding was raised (34/40px generic, 36/40px in the home rails) with matching more-negative margins so card positions are unchanged — overflow-y hidden on the track otherwise shears the top of the scale-up + glow on Home/Recommended rails (Continue Watching and posters). The glow now covers every focusable surface, not just cards: Back/Play/Watchlist/Options/More pills, season/library/alpha tabs, nav items, browse dropdowns and panel rows, search inputs, the profile PIN pad, calendar days, option rows and the detail facts table all get the same white glow (an override layer appended at the end of `styles.css` replaces the remaining per-control white outlines/rings). Verified on a physical TV by the user after the enlargement-clip fix. The rail also full-bleeds to both screen edges now: boundary tiles cut at the physical screen edge instead of ~50px short of it, and the end gutter rides inside the scroll as a flex-item spacer (`::after`, `flex: 0 0 6vw`, clamped 58-112px via min/max-width) instead of the rail's `padding-right`, because older TV web engines omit a scroll container's end padding from the scrollable area — that left the final tile flush at the clip line with its focus ring shaved. Verified rendered at rest and at max scroll: final tile fully inset with ring room, cut line at the screen edge, no overlap, no horizontal page scroll; re-verified on the live app against the test server (Dancing with the Stars S35, 8 episodes): boundary tile cuts at the screen edge at rest and the focused final episode renders with its complete ring ~92px inside the right edge at max scroll. Modal lock: the Options and More dialogs are focus traps; D-pad moves that would leave the menu snap back inside, and Back/Escape closes the menu (scrim click also closes). Series/movie hero action row: collapsed icon circles that expand to labelled pills on focus, with Play pinned open (Android-style circular utility actions; Play collapses only when another row button is focused). Up from the season pills lands on Play; Down from the action row returns to the last-viewed episode card (else the active season pill). Hero action row stability across episode changes (mirrors Android's `TvPlaybackSummary` / fixed-width series Play pill): the VERSION/AUDIO/SUBTITLES row is always rendered at a fixed height with fixed-width columns (skeleton bars only before the first value loads), previous values stay on screen while the next episode's detail resolves, the series page keeps the last loaded detail for the Options button so the row's buttons stop appearing/disappearing per episode, and the series Play/Resume pill reserves a 150px label width so Play↔Resume label changes do not shift the buttons after it; Start Over stays conditional on resume position, matching Android's `if (hasResume)`. Pre-play Options dialog on movie and series pages, mirroring Android's selector logic: editions grouped from `edition_raw`/`edition_key` (Auto hidden and the list scoped to the current edition when there are real edition choices), Android label set (4K · HEVC · DV · TrueHD, "Auto: …" annotations, language/codec/layout audio rows, SDH/Forced/Default/External subtitle rows), audio picked by zero-based ordinal and subtitles by the combined externals-first index, and manual picks persisted with `PUT /audio-prefs/{series_id}` / `PUT /subtitle-prefs/{series_id}` (signature bodies; version Auto prefers `user_data.last_file_id`). DV/HDR detection is approximated from codecs. Not yet matched: spoiler protection, episode long-press menu, theme music, watch party, translation controls, Go to Season/Series (standalone season/episode pages); unverified against a live server

### Release blockers
1. Validate the implemented Silo protocol-v3 planner/replan contract against a live server and official client behavior.
2. Token refresh with the exact Silo refresh endpoint and single-flight retry.
3. Validate the Silo-native catalog endpoints and response models against the live server.
4. Household profile creation/editing and full profile-management parity.
5. Validate playback progress/stop reporting and watched-state thresholds against the live server.
6. Subtitle styling plus intro/credits controls; validate the implemented audio/subtitle picker and chapters.
7. Validate codec/container matrix on at least one older and one current LG webOS generation.
8. Network-loss/reconnect UX and expired-session recovery.
9. Automated tests for navigation geometry, auth state, API parsing and player state.
10. Store assets, accessibility pass, privacy copy, trademark approval and LG certification checklist.
11. Side-by-side Android TV parity verification remains open. The client still lacks the Android inbox/notifications and person-detail flows; its detail screen omits cast/crew, trailers, facts, and version sections; audiobook detail/playback uses the generic video flow; and Back does not consistently return to the originating screen. Home metadata enrichment and LG-remote focus transitions also need verification. The sampled Home ambient tint is implemented, but artwork CORS behavior and physical-TV rendering still need validation; parity must not be claimed until the remaining gaps and device behavior are checked.
